One table of HTTP pairs vs a table per entity

This is a neutral technical comparison of tmornini/fusion-angle's storage design against a conventional relational schema with one table per entity. fusion-angle stores every write as one row in fa_message_pairs: "A pair is the request as received, or nothing, plus the response wire bytes" (SCHEMA.md). The conventional side is described generically and labelled as such.

Takeaway. The single-table design gives up SQL-level querying, per-field indexes, in-place migrations, storage compactness, and real deletion. In return it gets built-in optimistic concurrency with no extra column, wire-level history with stored hashes, and one uniform read and write path. A version column, history tables, or CDC can give a conventional schema the first two properties as well. What is specific to fusion-angle is that it keeps the exact request and response bytes.

The one table and its indexes

SCHEMA.svg is copied from the repo. It is generated from api/db.ts, api/types.ts, and api/schema-postgres.ts, and ./test validate fails on drift. The indexes it shows are fa_message_pairs_document (path, name, response_at, id), fa_message_pairs_collection (path, response_at, id), the unique fa_message_pairs_succession (path, name, supersedes) WHERE method IN ('PUT','DELETE'), fa_message_pairs_request_id, and the partial GIN fa_message_pairs_body (WHERE path = '/invitations/').

A typical request

Pages call client/ verbs, and client/http-facade.ts sends fetch(origin + '/api/' + resource). handleRequest runs framing, the id checks, auth, the fence, the conditional check, and then the pair plane (API.md § Dispatch order). A write appends rows in one statement (api/ledger-statement-sql.ts). A read selects heads (api/head-reads.ts) and serves the stored bytes through servedResponse, swapping the status line, date, and request-id.

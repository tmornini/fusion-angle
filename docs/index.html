HTTP request/response pairs as the stored data

A technical walkthrough of tmornini/fusion-angle for developers who build HTTP APIs: how it stores and serves data, and the tradeoffs involved.

Context

Many HTTP APIs map a request onto domain tables and build each response from those tables on every read, with ETags, version history, and lost-update protection implemented separately. Fusion Angle stores the exchange itself: "The API, the client, and the application treat a response — status line, headers, and body — as one unit" (ARCHITECTURE.md). The stored data is that unit.

Properties of the design

Pairs are the data

One table, fa_message_pairs. "A pair is the request as received, or nothing, plus the response wire bytes" (SCHEMA.md). A read "serves those stored bytes with exactly three substitutions — the status line, date, and request-id".

ETags are row ids

"The pair id is the ETag — If-Match names that identifier." No separate version column is used.

History by succession

Each write names its predecessor in supersedes. versions/ "joins every PUT as multipart/mixed, oldest first". A DELETE is a tombstone: "No physical delete exists."

Conflicts via a unique index

CREATE UNIQUE INDEX … fa_message_pairs_succession ON fa_message_pairs (path, name, supersedes) WHERE method IN ('PUT', 'DELETE') is "the only write enforcement". A stale If-Match "is 412".

How the pattern works covers the mechanics and tradeoffs in detail.

Summary of the mechanics

  • A document's address is path + name ("pathname = path + name, the URL API's word").
  • Its head is "its latest PUT or DELETE pair, and a head is its document's whole state".
  • Writes append. Reads select heads by index and serve the stored response. "The ledger stores writes only — no GET rows."
  • The application built on this storage is an innovation-management app with Ideas, Flow, Projects, Records, Workbox, Identities, and Account (README.md).

The request path

The steps

  1. Boot. web-app/app/server-core.ts builds the tab's one client: createAppClient(createHttpFacade(serverOrigin(), fetch)), then client.setCookieSession(true). Its own comment says: "Cookie-session: access token is memory only; refresh lives in the HttpOnly cookie."
  2. Page → client. "Page modules never call transport verbs from api/api.ts — data access goes through client/" (ARCHITECTURE.md § Conventions).
  3. Client → wire. client/request-context.ts adds OPERATION_ID_HEADER. "The client mints operation-id once per operation, on every request, and the server never mints one" (API.md).
  4. Dispatch. handleRequest mints request-id, then runs these steps in order: framing, carried Request-ID refusal, Operation-ID check, matchRoute plus authenticateRequest, the identity fence, body parse plus preconditionRefusal, Region B, the pair plane, and the handler (API.md § Dispatch order).
  5. Storage. A write appends pairs through one statement. A read selects heads and serves the stored bytes, with exactly three substitutions and three additions (ARCHITECTURE.md § A response is one unit).
  6. Fan-out. "A successful write notifies this tab via pub-sub and posts fusion-angle:data so other same-origin windows refresh. There is no LISTEN and no SSE client" (AGENTS.md).

# TEST-PLAN mitigation — F

- Section: F
- Cases: F56
- Expected: with pan mode ON, toggling Auto-Fit on and
  tapping the spacebar turns pan mode off cleanly with no
  toast — "exiting pan mode is always permitted."
- Observed: hunter reported the Auto-Fit toast appearing and
  pan mode staying ON. Reproduced twice by the hunter.
- Suspected layer: MCP (probable driving artifact)

## Did NOT reproduce from source

`web-app/app/flow-fsm-reduce.ts:689`:

    const turningOn = !state.isPanMode;
    if (turningOn && input.isAutoFit) { ...toast... }

Correctly ASYMMETRIC. With pan already on, `turningOn` is
false, the guard is skipped, and it falls through to
`isPanMode: false` — exactly what F56 requires.

`flow-interactions.ts:775-791` is a pure pass-through; its
`AUTOFIT_TOAST_MSG` comparison at :486 governs toast COOLDOWN
only. The one unconditional guard,
`presenters/flow-designer.ts:366 #guardAutoFit()`, is called
ONLY from `withZoomedIn():900` and `withZoomedOut():914` —
the zoom path, which is the correct behavior F29 verified
passing.

## Probable cause

The hunter's own note: it had to click the canvas to move
focus off the Auto-Fit switch before pressing Space. With pan
mode already ON, that click starts a pan gesture, making
`isGestureActive(state)` true, so `onSpaceToggle` returns
early with no toggle. Combined with a ~3s toast still on
screen from the Auto-Fit toggle itself, the reported symptom
follows with no defect present.

Corroboration: hunter R independently hit the same class of
artifact on R12, tracing an apparent panel-open failure to
`flow-interactions.ts`'s `isDbl`/`lastClick` timing being
confused by its own rapid repeated probing.

## Recommended action

Re-run F56 with NO intervening canvas click — toggle Auto-Fit
via keyboard, or wait out the toast and confirm no gesture is
active — before treating this as a defect. Not counted as a
validated regression in this run's summary.

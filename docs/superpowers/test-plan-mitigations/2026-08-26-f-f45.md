# TEST-PLAN mitigation — F

- Section: F
- Cases: F45
- Expected: after N renames, repeated Undo reverts each
  rename in turn, oldest included.
- Observed: after 11 renames, 10 reverted correctly but the
  OLDEST rename never reverted, across 5+ well-spaced Undo
  clicks that each answered HTTP 201 with Undo/Redo staying
  enabled (not exhausted).
- Suspected layer: API

## Mechanism (master source review, not reproduced)

Undo resolves SERVER-SIDE in
`api/derive-flows.ts:263 resolveFlowUndoTarget`. Two
fragilities, either of which yields the reported symptom.

### 1. Stack-bottom undo is a successful no-op

    const targetPointer = pointer - 1;
    const target = targetPointer >= 0
        ? stack[targetPointer] : undefined;

`api/routes.ts:4749` throws only when the WHOLE resolution is
undefined (flow missing). A resolution carrying
`target === undefined` still falls through to
`postFlowUndoOp`, which writes a pair and answers 201. An
exhausted stack therefore reports success, changes nothing,
and leaves Undo enabled — exactly "201, nothing happened,
still enabled."

### 2. Undo pairs are identified by TIMESTAMP

    const undoRequestAts = new Set(
        undoMessagePairs.map(mp => mp.request_at));
    ...
    if (undoRequestAts.has(
        storedById.get(mp.id)!.request_at)) pointer -= 1;

Identity by `request_at`, not by an explicit link. Two pairs
sharing a millisecond collapse in the Set, so `pointer`
decrements once where it should decrement twice and one step
becomes unreachable. This is a relationship inferred from
coincident clocks rather than declared — and it only bites
under fast repeated edits, which is precisely what F45 does.

## Recommended action

Reproduce with 11+ rapid renames while logging `stack.length`
and `pointer`. Then: make an exhausted undo answer something
other than 201 (or disable Undo at the stack bottom), and
link undo pairs to their target explicitly rather than by
timestamp equality.

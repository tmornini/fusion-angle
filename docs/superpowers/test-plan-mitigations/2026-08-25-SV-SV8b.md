# TEST-PLAN mitigation — SV

- Section: SV
- Cases: SV8b
- Expected: With two tabs signed in to the same organization, a
  write in tab A (e.g. creating an idea) reflects live in tab B's
  matching list, via the `fusion-angle:data` BroadcastChannel —
  same-tab-set cross-tab refresh, per AGENTS.md's documented
  pub-sub behavior.
- Observed: The BroadcastChannel transport itself works correctly —
  a raw `fusion-angle:data` listener attached directly in tab B
  received all 3 scoped messages broadcast from tab A's writes. But
  tab B's Ideas list never refetched or re-rendered in response (0
  new cards, no new network GET fired). Root-caused via source: in
  `web-app/ideas/index.ts`, `subscribeIdeaChanges` is wired only
  inside the `onIdeasLoaded` callback, which `loadInto`
  (`web-app/app/loading-states.ts:249-265`) invokes via its
  `onData` path — but `loadInto` takes the `emptyState` branch and
  returns *without* calling `onData` whenever the page's initial
  fetch returns zero items. A list page that starts out empty in a
  given tab therefore never registers its cross-tab subscription at
  all, and can never live-update via BroadcastChannel afterward, no
  matter how many broadcasts arrive — only a manual reload recovers
  it.
- Suspected layer: UI — `loadInto`'s empty-state early-return skips
  subscription wiring that should happen regardless of whether the
  initial fetch was empty.

**Likely systemic, not Ideas-specific.** `loading-states.ts` is an
app-level shared helper (also cited independently by case I21 in
the I section, for an unrelated loading-skeleton timing issue) —
its `loadInto`/`emptyState` pattern is almost certainly reused by
every list page (Projects, Records, Flows, Members, etc.), not just
Ideas. This was not independently confirmed on other pages during
this run — flagging the suspicion for whoever picks up this
mitigation to verify across pages, not asserting it as confirmed
fact beyond Ideas.

# TEST-PLAN mitigation — K

- Section: K
- Cases: K30
- Expected: In a project's View history modal, events render in
  chronological order, each row showing date/who/objective name
  (as of that event's moment)/detail, with baseline revisions as
  their own event rows.
- Observed: On the primary tested subject (an approved project,
  `k-project-approved`), K30's full checklist passed cleanly,
  including correct pre/post-rename objective-name resolution and
  baseline revisions as distinct rows. But an additional spot-check
  on a second project (`k-project-submitted`) found the "Objective
  archived" event row renders **entirely blank** — date, who,
  objective name, and detail all show "—" — and no "Objective
  reactivated" row appears anywhere in any history checked, even
  though K4/K5 (archive/reactivate) are both exercised elsewhere in
  this same test run.
- Suspected layer: UI/adapter — event-kind rendering specifically
  for archive/reactivate rows in the history view; every other
  event kind (creation, baseline revision, actual measurement,
  rename) renders correctly, so this looks isolated to those two
  event kinds rather than a general history-rendering defect.
  HIGH PRIORITY: a history/audit view that silently drops or blanks
  event data undermines the same temporal-integrity guarantee K7
  (in this same section) exists to verify — an audit trail that
  goes quietly blank is exactly the kind of failure a project
  history feature exists to prevent.

# TEST-PLAN mitigation — F2

- Section: F2
- Cases: WB5a
- Expected: Recreating a deleted edge (Data Capture → Archive
  "submit" transition) via Delete+Undo restores the flow to READY,
  and the Workbox Active tab continues showing every unclaimed/
  in-progress work order on that flow, same as before the edit.
- Observed: The gesture itself (port-drag to recreate the edge) is
  a known, sanctioned MCP pointer-capture limitation, worked around
  correctly via toolbar Delete+Undo — the flow readiness check
  (NOT READY → READY) behaved exactly as documented through that
  cycle. But after the edit+undo cycle completed, the Workbox
  Active tab showed **0 items for every work order on that flow**,
  including a brand-new work order created after the restore — even
  though the flow itself is READY/healthy, and other views (a
  direct work-order URL, and the Records page's "work orders using
  this record" list) correctly showed all 4 work orders still
  existing and healthy. Only the Active-tab inbox view is affected.
- Suspected layer: UI/adapter — looks like a
  `buildInboxItems`/`transitionsByWo` presenter-derivation
  regression triggered by the flow graph's edit+undo cycle
  (`web-app/app/presenters/workbox-inbox.ts` derives inbox items
  from `transitionsByWo`; something in that derivation appears to
  go stale or empty after the graph mutates and is then undone).
  HIGH PRIORITY: this silently empties a live, frequently-used
  inbox view with no error surfaced to the user — exactly the
  "silent corruption" failure mode the codebase's own doctrine
  singles out as worse than a visible failure.

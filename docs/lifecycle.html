Tradeoff 3: does "no migrations" just move the schema into application code?

Largely, yes. The body shape is defined and validated in TypeScript (api/types.ts, api/validators.ts, serializeValue in api/storage-serialize.ts), and read back through 19 api/derive-*.ts folds. Since old versions are never rewritten, each reader carries the compatibility burden. When the table itself changes, the shipped answer is wipe and reseed, which is only possible before tenant data must be kept. TODO.md's "Table migrations" bullet activates exactly then. No planned view decodes bodies into columns (item 0f: "a view is only ever a device").

Tradeoff 5: the privacy cost of never physically deleting, including erasure requests

Shipped: PII "erasure" appends a bodyless DELETE head, and the superseded PII pairs remain (SCHEMA.md § PII erasure is a tombstone; tests/api-pii-tombstone.test.ts 'erased PII remains in superseded pairs; login is 401'). Credential lines are stored in plaintext. Item 0f would hide these from the API role, but any dump still carries them. Physical erasure is planned behind a trigger. It removes the bytes and gives up the complete history of those pairs, while an erasure pair keeps their ids and hashes. Backup and WAL windows remain to be stated. Request-body PII, such as an invitation email, is an open question.

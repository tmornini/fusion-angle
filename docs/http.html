HTTP compliance

Status codes come from the API layer, not from storage. A per-entity application can return 304, 409, 410, 412, and 428 too. So this page compares the work required in each design, then lists every code fusion-angle actually emits and checks it against RFC 9110. The canonical list is shared/http-errors.ts:54-72, at master f0382d4.

Deviations and gaps, recorded as cons against fusion-angle

Verdicts reflect shipped behavior, so these remain gaps.

  • Planned (TODO.md "Cachability") API 405 responses omit Allow, which §15.5.6 makes a MUST (api/api.ts:1008 and siblings).
  • Planned (pending TODO.md PR) 401 responses carry no WWW-Authenticate (§15.5.2, RFC 6750 §3) (api/request-auth.ts:82).
  • Planned (TODO.md "Cachability") There is no conditional GET: no 304, and no If-None-Match or If-Modified-Since on reads, even though every read has a strong ETag and Last-Modified.
  • Planned (pending TODO.md PR) One strong ETag can name differently projected bodies, with no Vary. no-store mitigates caching, not validator semantics.
  • Planned (pending TODO.md PR) Debatable: 504 for a database timeout (api/errors-postgres.ts:92), where an origin would normally send 503. Debatable: 412 rather than 400 when both preconditions are sent (api/api.ts:258). Unused: 422 is defined but never emitted. Unverified: 501 for unimplemented auth methods, and the catch-all UniqueConstraintError → 412.
  • Planned (TODO.md "API retries, unified") Optional: no Retry-After on 429.

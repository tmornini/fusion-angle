Example: count ideas by state

Single-table (fusion-angle)

-- heads of /ideas/ for one org, then
-- parse each body in TypeScript
-- (api/backend-postgres.ts
--  COLLECTION_HEAD_PAIRS_SQL)
CROSS JOIN LATERAL (
  SELECT * FROM fa_message_pairs head
  WHERE head.path = $1
    AND head.name = names.name
    AND head.method IN ('PUT','DELETE')
  ORDER BY head.response_at DESC,
           head.id DESC
  LIMIT 1) heads
WHERE heads.method = 'PUT'

The group-by then runs in application code over the parsed bodies. An ad-hoc count of ideas by state would need fa_message_body_json(response)->>'state' over every head. Invitations are the exception: they filter in SQL with @>, and organization_id is the GIN condition. What is missing is a join on a body field.

Conventional (generic)

SELECT state, count(*)
FROM ideas
WHERE organization_id = $1
GROUP BY state;

Conventional and illustrative. Columns are typed and indexable.

Tradeoff 1: are reporting, joins, and aggregates practical when fields live inside HTTP bodies?

Shipped: not in SQL. Fields sit in response bytea after the header block. Every family derives in TypeScript through one parser (bodyOf, api/derive-documents.ts), and cross-entity work is application code. The design spec warns that filtering before head selection "lets a superseded version's match elect the wrong head" (docs/superpowers/specs/2026-09-04-one-table-examined-design.md). So a correct SQL filter has to pick heads first and filter after. Invitations are filtered in SQL: fa_message_body_json(response) @> a containment, and organization_id is the GIN index condition. What is missing is a join on a body field. Other families still derive in TypeScript.

Planned: fa_reporter (Trigger, undefined) and body-field filtering (Later). Not planned: a view that decodes bodies into columns, which would bring a SQL schema back. Report query speed is unmeasured.
